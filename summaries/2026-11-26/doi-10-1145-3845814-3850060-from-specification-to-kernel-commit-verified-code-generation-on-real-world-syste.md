## 论文针对什么问题

论文针对的是 **真实世界系统中的验证代码生成（verified code generation）** 问题。所谓验证代码生成，是指让 LLM 同时生成实现代码和正确性证明，从而走向“按构造保证正确”的软件。

作者指出两个关键问题：

1. **旧的评估方式过时**：此前对 LLM 验证代码生成能力的评估大多在“bare-model”设置下进行，即直接调用模型，而不像实际部署中那样把 LLM 作为 coding agent 使用。因此在真实使用方式下，LLM 的能力可能被低估或误判。

2. **旧基准已经饱和**：作者重新评估现有基准后发现，coding agents 在来自编程竞赛等研究充分来源的任务上“几乎全部解决”。这说明这些基准已经无法区分现代 agent 的能力，也无法代表真实系统场景。

因此论文要回答的核心问题是：**在编程竞赛式任务上的成功，能否迁移到真实世界的系统任务上？** 换言之，真实世界中的验证代码生成是否仍然是一个开放问题。

## 提出了什么解决方案

作者提出一个新的基准：**Vero**。

Vero 由 **103 个验证代码生成任务**组成，来源于三个对安全性和正确性要求极高的真实项目：

- Linux 内核 eBPF verifier
- LLVM 编译器
- seL4 微内核

每个任务都具有以下特征：

- 来自真实世界系统；
- 编码了一个新的规范；
- 如果被正确解决，将直接有利于上游项目。

作者用 Vero 评估三个 coding agents，以衡量当前真实世界验证代码生成的实际能力，并为未来工作提供未解决任务作为具体目标。

## 具体是怎么做的

摘要披露的方法论如下：

1. **重新评估现有基准作为动机验证**  
   作者在 coding agent 设置下重新测试既有验证代码生成基准，发现对编程竞赛等来源的任务，agents 几乎全部解决。  
   *但具体重新评估了哪些基准、使用哪些 agents、成功判据是什么，摘要未提供。*

2. **构建 Vero 基准**  
   从 Linux kernel eBPF verifier、LLVM 和 seL4 三个项目中收集 103 个真实任务。  
   摘要仅说明任务需要满足：真实世界、包含新规范、正确解对上游有价值。  
   *但任务如何抽取、规范如何编码、证明格式是什么、使用什么证明检查器或验证器，摘要未提供。*

3. **评估三个 coding agents**  
   在三类真实系统任务上运行三个 coding agents，报告最强 agent 仅解决 3/103。  
   *但三个 agents 的名称、是否允许执行反馈、是否允许使用验证器错误信息迭代、尝试次数、时间预算、成功判据等，摘要未提供。*

4. **记录一个上游合并案例**  
   一个 agent 发现的 Vero 任务解决方案已经被合并进 Linux 内核：它用 4 行可证明正确的算法替换了领域专家提出的 20 行算法。  
   *但具体是哪个内核补丁、对应任务、证明如何被内核社区接受，摘要未提供。*

由于本次没有 PDF 正文，更细粒度实验设置无法确认。

## 取得了什么效果

摘要给出的主要结果如下：

1. **旧基准已不再具有区分度**  
   在 coding agent 设置下，编程竞赛等来源的现有任务几乎被全部解决。

2. **真实世界验证代码生成仍接近未解决**  
   在 Vero 上，最强的 coding agent 仅解决 103 个任务中的 3 个，即约 2.9%。论文据此判断真实世界 verified code generation 仍然是开放问题。

3. **存在真实系统价值证据**  
   一个 agent 生成的方案被合并到 Linux 内核，替换 20 行专家算法为 4 行可证明正确算法，说明该方法在关键系统代码中有潜在应用价值。

4. **为后续研究提供具体目标**  
   未解决任务可以直接作为未来改进的对象。

## 旁观者视角的问题与不足

从外部读者视角看，摘要中的若干信息不足，限制了对结论强度和可复现性的判断：

- **缺少对照基线**：摘要只报告 agents 在 Vero 上 3/103 的结果，没有给出 bare-model 在 Vero 上的表现、人类专家表现，或传统程序合成/形式验证工具的表现。单看 3/103，很难判断失败主要来自 LLM 推理、agent 工具链、证明生成难度，还是基准设计。

- **实验设置不透明**：未说明三个 coding agents 是什么、是否允许使用验证器反馈进行多轮迭代、是否有搜索预算、是否每个任务只尝试一次、规范是否由任务直接给出还是需要从真实项目上下文中提取。这些变量对成功率影响很大，外部难以判断“3/103”在什么条件下成立。

- **基准代表性和分布不明**：103 个任务虽然来自三个项目，但未给出任务数量分布。如果大部分任务集中在 eBPF verifier 的某类边界条件，结论可能更偏向该子域，而不是整个真实世界系统验证问题。

- **“旧基准几乎全解”缺乏具体数据**：摘要没有给出重新评估的基准名称、任务数量和成功比例。“nearly all tasks”作为动机很强，但可复核性不足。

- **单个内核合并案例需要谨慎解读**：一个 agent 方案被 Linux 内核合并是强信号，但摘要未说明该补丁是否被人工改写、是否经过额外验证、是否属于特别适合 agent 的任务。单个成功案例不足以证明方法端到端可靠。

- **“verified”定义未展开**：生成证明由什么工具检查、是否与项目既有形式化框架一致、证明是否自动可验证，摘要均未提供。这影响对“provably correct”实际含义的判断。

## 值得继续追踪的点

- **Vero 基准是否公开可复现**：任务清单、评估 harness、证明检查接口、agent 配置和成功判据是否发布。
- **更强 coding agent 的后续表现**：是否有新模型或新 agent 在 Vero 上明显超过 3/103，以及失败原因是否被系统分析。
- **Linux 内核合并案例的细节**：具体 commit、对应任务、证明如何被内核社区接受，以及该代码后续是否被维护或替换。
- **方法在更多系统项目中的扩展**：是否覆盖其他安全/正确性关键项目，如 Dafny、Coq、Lean、F* 等证明系统生态。
- **失败任务的结构性分析**：失败来自规范理解、证明构造、验证器接口，还是 agent 工具链限制。
- **与形式验证、程序合成和 LLM agent 路线的交叉改进**：验证反馈、检索增强、fine-tuning 等手段能否提升真实世界 verified code generation 的成功率。
