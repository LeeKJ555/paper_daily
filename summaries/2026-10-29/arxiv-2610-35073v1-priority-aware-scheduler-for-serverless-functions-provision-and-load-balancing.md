## 论文针对什么问题

论文针对 Serverless / FaaS 场景中的冷启动问题，以及现有调度与资源管理策略的不足。具体包括：

- 冷启动持续影响系统性能，现有预加载 / 卸载策略过于简化，没有充分挖掘函数调用模式。
- 现有方法难以在启动延迟和资源效率之间取得最优权衡。
- 很多方法忽视了内存受限的多 worker 节点这一实际约束，导致函数驱逐和负载不均问题加剧。
- 需要一种在内存受限的分布式 worker 集群中同时考虑函数供给、驱逐和负载均衡的调度方案。

## 提出了什么解决方案

论文提出 **SPES-Ext**：一个基于规则的、优先级感知的 Serverless 函数调度器，面向内存受限的分布式 worker 节点。

方案来自两个关键观察：

1. Serverless 系统具有集中的调用模式，因此行为具有可预测性。
2. 这些调用模式允许对函数进行分类，从而支持更细粒度的实例管理。

基于“特征驱动的优先级能够促成最优调度规则”这一思想，SPES-Ext 集成了三个协同模块：

- 预测式函数供给（predictive function provisioning）
- 驱逐优化（eviction optimization）
- 动态负载均衡（dynamic load balancing）

## 具体是怎么做的

从摘要和正文摘录中可以看到以下设计要点：

- 总结典型调用模式，并据此对函数进行分类，作为差异化供给策略的基础。
- 提出一种“co-occurrence”指标，用来度量函数之间的关联性。
- 提供了自适应策略，并处理 unseen functions 的情况。
- 在 Microsoft Azure 发布的工业数据集上进行评估。
- 消融实验验证了 inter-function connection、自适应策略以及负载均衡调度的有效性。

不过，正文摘录和摘要未提供足够信息来完整还原以下细节：

- 预测式函数供给的具体算法与优先级规则。
- 驱逐优化的具体决策指标和阈值。
- 动态负载均衡的具体调度机制。
- 规则如何编码、更新和维护。
- 训练 / 统计周期、窗口大小、内存约束数值等实验配置。

因此，上述模块的内部实现细节需要查阅论文完整正文。

## 取得了什么效果

论文报告的主要实验结果为：

- 与基线相比，75 分位冷启动率降低 80%–90%；摘要中的表述为“80% reduction in 75th-percentile cold starts”。
- 内存浪费时间降低 83.92%–88.82%；摘要中的表述为“83.92% decrease in memory waste”。
- worker 负载方差改善 52.49%–96.14%；摘要中的表述为“52.49% improvement in worker load variance”。
- “always-cold”函数的比例显著降低。
- 消融实验表明 inter-function connection、自适应供给策略和负载均衡调度均有效。
- 论文声称 SPES-Ext 引入的计算开销很小。

需要说明的是，摘要只给出了部分指标值，正文摘录给出的范围更宽。论文未在给定材料中详细说明基线列表、worker 数量、内存限制、函数规模、冷启动定义和实验重复次数等，因此无法确认这些数字在何种具体实验设置下取得。

## 旁观者视角的问题与不足

从系统和工程角度看，有以下具体观察：

- 只强调 75 分位冷启动指标，未在摘要 / 摘录中看到 p99、平均冷启动延迟、尾延迟或端到端延迟，难以判断对长尾请求的影响。
- 摘要中的“80% reduction in 75th-percentile cold starts”表述比较模糊：不明确是冷启动次数、冷启动率还是冷启动延迟的降低。
- 论文似乎依赖函数分类和 co-occurrence 模式。对于调用模式稀疏、突发性强、或者函数频繁新增 / 下线的场景，规则和优先级的稳定性存疑。
- 缺少多 worker 内存受限环境的详细配置信息，例如 worker 数量、每 worker 内存上限、函数内存规格、并发模型等。
- 正文摘录提到负载方差改善幅度为 52.49%–96.14%，范围较大，说明效果可能高度依赖场景；摘要只取 52.49% 作为代表值，容易高估或低估不同配置下的表现。
- 没有在已给材料中看到与学习型调度器、强化学习或更复杂的预测模型的直接对比，难以判断“基于规则”的方案在动态工作负载下是否真的优于数据驱动方法。
- “small computation overhead”没有给出具体数值，无法评估调度器本身对 worker CPU / 内存 / 延迟的影响。
- 缺少对 co-occurrence 指标维护成本、图规模增长、过期关系处理等系统复杂度的分析。

## 值得继续追踪的点

- SPES-Ext 的完整规则设计、优先级计算方式和调度决策时延。
- 在真实多 worker、内存受限集群上的部署表现，尤其是 worker 数量扩展时的负载均衡效果。
- 更细粒度的冷启动指标：p50 / p75 / p95 / p99 冷启动延迟，以及冷启动比例。
- 与数据驱动或学习型 Serverless 调度器的对比，特别是在非稳态工作负载和突发流量下。
- co-occurrence 图的更新机制、自适应策略如何应对函数调用模式随时间漂移。
- 是否开源代码、数据集和实验配置，以便复现和验证 80%–90% 冷启动率降低等结论。
- 调度器自身开销的定量分析，例如额外 CPU 使用、内存占用和调度延迟。
- 该规则方法能否跨云平台、跨运行时和跨语言泛化。
