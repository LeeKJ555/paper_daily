## 论文针对什么问题
图近似最近邻搜索（ANNS）是向量数据库和检索增强生成（RAG）流水线中的核心算子，但大规模向量索引常超出单 GPU 服务器内存。NVMe-oF 提供了诱人的存储分解方案，但现有远程 I/O 路径仍以 CPU 为中心：由 CPU 构造 I/O 请求、驱动传输进度并决定 GPU 何时恢复计算。这种组织方式与图 ANNS 的工作模式严重不匹配——下一次数据访问是在 GPU 图遍历过程中动态发现的，CPU 介入不仅带来控制转移开销，还让 GPU 失去对搜索调度的主动权，难以有效重叠计算与远程 I/O。

## 提出了什么解决方案
提出 **GORIO**，一个将 GPU 中心的本地 I/O 扩展到远程 NVMe-oF 存储，并针对图 ANNS 特化的系统研究。其核心思想是**将查询演进、页缺失生成、待处理查询状态和恢复决策全部留在 GPU 上**，而 CPU 仅充当 NVMe-oF 传输和完成操作的代理。GORIO 包含两层设计：
1. **GPU 直接远程 I/O 路径**：将 GPU 本地页缓存缺失转化为分阶段（split-phase）远程操作，避免 GPU 线程原地阻塞。
2. **ANNS 专用调度机制**：在图遍历过程中主动暴露缺失，并调度其他就绪查询的计算，使得 **图遍历与远程页服务能够重叠执行**。

## 具体是怎么做的
- **整体架构**：以 BaM（GPU 可见页缓存）为基础，扩展 SPDK 作为 NVMe-oF 启动器，通过 RDMA 连接远端 NVMe 命名空间。GPU 页缓存中的数据直接位于 GPU 可访问内存，避免通过主机侧缓冲区进行二次拷贝。
- **GPU 侧**：图遍历内核在发现所需页不在 GPU 缓存时，记录依赖关系并发布请求描述符（而非阻塞等待），随后持久化调度器（persistent scheduler）选择其他就绪的查询继续执行。GPU 维护就绪表（ready table），当远程页数据就绪且状态被推送回显式 GPU 可见内存后，对应查询被重新标记为可恢复。
- **CPU 代理**：专职完成 NVMe-oF 命令的提交、批处理与完成轮询。从 GPU 描述符转换为 NVMe-oF 读命令，将返回数据直接写入 GPU 缓存槽，并更新就绪状态。代理不检查候选队列、图前沿或查询终止状态，从而将 ANNS 调度完全留在 GPU 侧，CPU 仅提供传输服务并控制未完成请求的深度，保证传输效率。
- **实现**：C/C++/CUDA/SPDK 混合实现，集成 GustANN 风格的图搜索负载，并同时提供两个具体变体——G‑Gust（将 GORIO 远程 I/O 路径与异步查询调度器结合）和 G‑ABaM（在 BaM 式按需分页模型上添加 ANNS 感知的 GPU 调度）。

## 取得了什么效果
在 **SIFT1M DiskANN 风格图** 工作负载（10000 条查询，recall@10）上，使用两台服务器通过 **InfiniBand (200 Gbps) NVMe-oF** 连接远端子磁盘（华为 3.84 TB NVMe SSD）进行端到端评估。主要对比路径和结果如下（表 2）：

| 系统路径 | 时间 (s) | QPS   | 加速比 (相对参考) |
|----------|----------|-------|-------------------|
| G‑Gust   | 0.99     | 10,058 | **1.31×** vs. GustANN；121× vs. GDS |
| GustANN  | 1.30     | 7,680  | 参考（先进远程 I/O 路径） |
| G‑ABaM   | 1.77     | 5,650  | **4.89×** vs. BaM；68× vs. GDS |
| BaM      | 8.66     | 1,155  | 14× vs. GDS        |
| GDS      | 120.19   | 83     | 基线（直接远程页缓存路径） |

- GORIO 的 G‑Gust 配置比当时最先进的远程 I/O 参考路径 **快 1.31 倍**，比直接远程页缓存路径（BaM 式阻塞等待）**快 4.89 倍**（G‑ABaM 对比 BaM）。  
- 在所有对比中，GPU 一直保持搜索调度主导权，证实了 GPU 拥有的页缺失生成、待处理状态和恢复决策能够高效驱动真实的 NVMe‑oF 存储，无需将图遍历调度交回 CPU。

## 旁观者视角的问题与不足
- **评估规模有限**：仅使用 SIFT1M（百万级）数据集和一种图构造方式。论文自身也指出需要扩展到更大索引（如十亿级）和更多数据集，以观察在更深的图层次、更大工作集、不同召回目标下的行为。
- **硬件和网络单一**：实验基于 InfiniBand 200 Gbps，未覆盖广泛部署的 RoCE 或 TCP 类 NVMe‑oF 传输。远端仅连接单块 SSD，未考察多盘、多目标端的扩展性。
- **GPU 页缓存策略未详述**：论文没有报告 GPU 缓存大小、替换策略对查询延时/带宽的影响分析，也缺乏缓存命中率、预取有效性等微观数据。
- **集成视野不够**：目前系统是基于 BaM 和 GustANN 的原型，未展示如何嵌入到现有向量数据库或类似 DiskANN/HNSW 的实现中，也没有讨论与 GPU 直接存储（GDS）或 GPU 编排内存分层（如 GMT）的定量对比。
- **多 GPU 和多租户场景缺失**：未说明在多 GPU 共享远程存储或并发查询负载下的调度公平性、缓存一致性以及传输代理 CPU 的瓶颈效应。
- **CPU 代理的开销**：虽声称 CPU 不参与调度，但代理的批处理、完成轮询等操作对尾延迟的影响未量化。

## 值得继续追踪的点
- 在 **SIFT1B、DEEP1B 等大规模数据集** 上验证 GORIO 的页缓存行为和端到端加速，尤其考察长图遍历中的异步重叠收益。
- 将 GORIO 远程 I/O 路径 **集成到实际向量数据库引擎**（如 Faiss、Milvus、或 DiskANN 官方实现）中，观察集成复杂度和实际性能提升。
- 探索 **计算型存储（CSD）或存储端近数据计算** 与 GORIO 的结合，进一步卸载距离计算或图扩张操作。
- 面向 **多 GPU 和分布式 GPU 集群** 扩展页缓存共享、远程 I/O 调度，分析 CPU 代理在多种负载下的可持续性。
- 研究 **动态页缓存管理和基于查询模式的预取策略**，以适配不同召回率目标和向量分布。
- 与更多 **GPU 中心的存储方案**（如 GMT、GNStor 等）进行横向对比，理清各自的设计取舍和适用边界。
